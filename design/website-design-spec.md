# LunaDeerMC 官网设计说明

> 本文档是 LunaDeerMC 官方网站的设计事实源。已确认的结论优先级高于早期提案和聊天记录。后续讨论产生明确结论时，应同步更新本文档。

- 项目：LunaDeerMC 官方网站
- 类型：纯静态官网与文档站
- 文档更新日期：2026-08-02
- 当前阶段：设计与技术基线已确认，准备进入正式实现

## 1. 项目定位

LunaDeerMC 是一个 Minecraft 开发组织，作品范围包括：

- Minecraft 插件
- 服务端核心
- 开发工具与组件

作品可以是免费、付费或同时提供免费版与专业版。官网本身不处理付款和订单，需要获取付费作品时，将用户引导至第三方平台。

网站有两个核心职责：

1. 展示作品，帮助用户了解、选择、下载或获取作品。
2. 托管作品与通用文档，帮助用户安装、配置和使用作品。

网站全局支持中文与英文。中文是默认语言并保持现有无前缀 URL；英文统一使用 `/en` 前缀。除具体文档外，所有公开静态页面必须同时具有中文和英文版本；文档允许只有一种语言，缺少对应翻译的目标路径直接进入该语言 404。双语内容源组织方式将在国际化专题中确定。

## 2. 用词规范

### 已确认

所有面向用户的“产品”语义统一更换为“作品”，以降低商业化和商城感。

应使用：

- 作品
- 全部作品
- 精选作品
- 作品介绍
- 作品文档
- 已归档作品
- 其他相关作品

面向用户的路由使用 `/works`，不使用 `/products`。

## 4. 全站导航

顶部导航的完整结构、外观、功能菜单和响应式规则由[全站导航系统](./navigation-system.md)统一维护，本节只记录其核心结论，避免在总说明中形成第二份容易不一致的详细定义。

```text
[LunaDeerMC  支持  关于]              [作品  文档  功能菜单]
        组织与品牌                         内容与工具
```

- 全站导航使用统一内容结构和交互模型，并为品牌页面与内容页面分别提供浅色和深色外观。
- 功能菜单提供全站搜索、中英文语言切换，以及“跟随系统／浅色／深色”主题模式。
- 导航随宽度按固定顺序逐级收纳：先将作品与文档收入菜单，再在非常窄的屏幕上将支持与关于收入菜单，Logo 始终保留。
- 精确断点根据最终 Logo、字体和间距测量确定，不使用设备名称代替真实空间判断。
- 法律政策统一放在页脚。
- 外部链接需要明确的外链标识。
- GitHub、社区和购买平台等外部渠道不直接挤入顶部导航。

## 5. 首页

### 已确认的首屏文案

```text
LunaDeerMC

To the moon, to the dream, to the future!

为 Minecraft 社区构建可靠易用的插件、
服务端核心与开发工具。

[浏览作品]  [查看文档]
```

### 已确认的内容结构

首页应轻量，不承担完整作品目录或大量说明内容。这里的“轻量”只限制内容数量与信息密度，不限制视觉表现力；首页可以通过构图、空间、光影、动态背景和转场形成沉浸式的品牌第一印象。

首页的四层 Minecraft 单一场景、远慢近快的视差关系，以及近景与精选作品同色过渡已经确认。深色模式采用“黄昏红石工坊”，浅色模式采用“白天牧场”，并分别使用独立四层资产。语义色板、首页内容顺序和精选作品等权关系已经确认；正式场景素材、精确速度、滚动距离和 Hero 退场曲线在首页开发阶段以真实资产和录屏校准。旧原型素材和参数不得直接进入正式工程。

```text
首屏
→ 精选作品（存在精选候选时）
→ 等权的文档与支持入口
→ 简短的组织介绍
→ Quiet Field
→ Horizon Veil
→ 页脚
```

首页完整内容职责由[首页内容系统](./homepage-content-system.md)维护。精选作品不使用“一件主作品＋若干次级作品”的主次构图；当前显示的作品使用相同的视觉与内容结构。

精选候选由 `src/content/works/{work}/data.yaml` 中的 `featured: true` 生成。静态构建保留完整候选集合，浏览器每次加载首页时随机展示最多三件并随机排列；同一页面生命周期内滚动和主题切换不重新抽样。候选为空时完整省略精选作品内容，不展示空状态或虚构作品。

文档与支持属于同一个宏观章节，并以相当的空间、标题、说明和操作重量呈现。文档负责引导安装、配置与深入使用；支持负责引导社区、获取、赞助与政策。首页不展开文档树、支持渠道或政策明细。

## 6. 作品列表

### 页面目标

作品列表应当像一个克制的作品集，而不是商城商品目录。用户应当能够快速感受作品的视觉和用途，再进入介绍页了解作品特色、技术信息与获取方式。

### 当前方案，待视觉稿确认

页面使用“简短开场＋轻量筛选＋双列视觉列表”的结构：

```text
作品
一句简短说明

全部    插件    服务端核心    工具与组件       [筛选]

[大尺寸作品封面]             [大尺寸作品封面]
作品名称                         作品名称
一句说明                         一句说明
插件 · 开源                     服务端核心 · 免费＋专业版

[大尺寸作品封面]             [大尺寸作品封面]
……                               ……
```

### 页面开场

- 只使用“作品”主标题和一句说明。
- 不展示作品数量、下载数据、更新统计或分类介绍。
- 与顶部导航和列表之间保持充足留白，但不设置第二个大型首屏。

### 分类与筛选

- 顶层分类直接平铺：全部、插件、服务端核心、工具与组件。
- 分类切换采用文字导航或轻量分段控件，不使用彩色实心胶囊。
- 获取模式、开源状态和维护状态收入一个次级筛选面板。
- 当次级筛选生效时，在筛选入口附近给出克制的已启用状态。
- 筛选条件同步至 URL，以便刷新、前进、后退和分享。
- 全局搜索已经可用时，作品列表不再放置一个显眼的重复搜索框。

### 作品列表项

- 桌面端使用两列宽松网格，移动端使用单列。
- 封面为列表项的主要视觉，建议使用统一比例的真实截图、作品视觉或精心制作的封面。
- 封面下只展示名称、一句说明、作品类型和一个必要状态。
- 说明最多两行，不在列表中展开功能、兼容版本和获取按钮。
- 整个列表项可点击，不额外放置强调色主按钮。
- 悬停反馈以轻微图像缩放、文字颜色变化或箭头位移为主，不使用大幅上浮和强阴影。
- 已归档作品使用降低对比度的状态标识，不将整张封面处理为无法辨认的灰色。

### 列表长度

- 第一阶段直接生成全部匹配作品，不使用无限滚动。
- 当作品数量达到需要分页的规模时，优先使用静态分页而不是“加载更多”。
- 无匹配结果时，使用简短文字说明并提供“清除筛选”操作。

## 7. 作品介绍页

### 已确认的定位

`/works/{work}` 称为“作品介绍页”，不称为“作品详情页”。

作品介绍页仍然是作品在官网中的介绍主页。使用 `index.mdx` 的默认模式参考 Modrinth 项目页的信息组织方式并适当简化；使用 `index.astro` 的特殊作品仍然可以拥有完全独立的视觉、布局和特效。两种模式都需要先说明作品的价值和特色，再帮助用户找到文档、获取方式和其他资源。

新作品可能约每半年才发布一件，因此网站需要保留为重要作品单独设计页面的空间；与此同时，简单作品不必为了发布而重复开发一整套页面。

### 已确认的实现策略

- 作品介绍页支持“默认骨架”和“自定义主页”两种实现模式。
- 当入口文件是 `index.mdx` 时，构建系统自动套用统一的默认作品介绍页骨架。该模式适用于功能简单、没有必要单独设计主页的插件、工具或组件。
- 当作品需要更有特色的布局、视觉和特效时，使用 Astro 原生页面源码 `index.astro`。自定义主页不使用 MDX，也不套用默认骨架。
- 每个作品目录只能存在一种入口：`index.mdx` 或 `index.astro`，不能同时存在两种入口。
- `index.mdx` 执行完整 Frontmatter、正文与索引数据一致性校验；`index.astro` 只执行作品共有数据、编译、路由、资源、链接和最终 HTML 基础检查，不要求导出默认模板字段。
- 自定义主页可以独立设计、独立编排和独立实现；不强制使用共享的作品区块组件，也允许为了独特布局和特效重复实现相似能力。
- 能够自然复用的全站能力仍可以复用，但复用不应成为限制自定义主页创意的硬性条件。
- 两种模式都必须完成桌面端和移动端设计，不在完成桌面端后再简单压缩。

单个作品目录示例；完整目录结构以第 12 节为唯一依据：

```text
src/content/works/
├── simple-work/             # 使用默认介绍页骨架
│   ├── data.yaml            # 列表、搜索和全站关联数据
│   ├── index.mdx            # 默认骨架配置与“介绍”正文
│   ├── components/
│   └── styles/
└── featured-work/           # 使用 Astro 原生的自定义主页
    ├── data.yaml
    ├── index.astro
    ├── components/
    └── styles/
```

`data.yaml` 与介绍页源码共同放在对应作品目录中。它不负责控制页面设计，只提供列表、搜索、文档关联、SEO 和其他全站功能需要的稳定数据。

### 默认介绍页骨架

默认骨架根据同目录的 `data.yaml` 和 `index.mdx` 生成页面。它提供一致的排版和基础能力，但只渲染当前作品确实具备的内容，不要求填满所有区块。

默认骨架固定使用以下主要结构：

```text
作品头部
图标｜名称｜一句简介｜状态与访问模式｜查看文档

介绍｜图库｜版本与更新｜获取方式
──────────────────────────
标签页主要内容           兼容性
                       相关链接
                       作品信息
```

- 作品名称、简介、图标、状态、访问模式和兼容性来自同目录的 `data.yaml`。
- 右上角主要按钮为“查看文档”，读取 `data.yaml.docs.root`；没有关联文档时不显示。
- “介绍”使用 `index.mdx` 正文。
- “图库”根据 `index.mdx` Frontmatter 的 `gallery` 生成，没有图片时隐藏。
- “版本与更新”根据 Frontmatter 的 `github` 地址在页面加载后由浏览器读取公开 GitHub Releases，没有地址或可用 Release 时隐藏。
- “获取方式”根据 Frontmatter 的 `acquisition` 生成，支持免费、付费和免费加付费档次。
- `early-access` 和 `active` 作品必须提供获取方式；`archived` 作品可以省略，仍可获取的归档作品也可以继续保留。
- 右侧信息栏只保留兼容性、必要相关链接和作品信息，不照搬下载量、关注数、创作者列表、密集标签和复杂筛选。

`index.mdx` 是默认作品页的结构化配置和“介绍”正文入口，不属于该作品的文档集。MDX 正文不控制页面整体布局，也不重复编写作品一级标题。安装、配置和使用文档仍然放在独立的 `docs/` 目录中。

完整 Frontmatter 字段、类型和校验规则以[技术架构：默认作品页 Frontmatter](./technical-architecture/default-work-page-frontmatter.md)为准。

### 自定义主页可以自由变化的内容

- 首屏布局、主视觉、背景、字体组合与局部强调色。
- 内容区块的数量、顺序、宽度和组合方式。
- 沉浸式图片、游戏截图、视频、3D 或其他作品专属媒体。
- 滚动叙事、视差、转场、交互演示以及作品专属动效。
- 兼容信息、版本对比、获取入口和 GitHub 更新的具体视觉形式与出现位置。
- 其他只与当前作品相关的专属介绍内容。

### 仍然统一的作品数据

无论使用默认骨架还是自定义主页，用于作品列表、全站搜索、文档关联和 SEO 的基础数据都在同目录的 `data.yaml` 中保持统一：

- 作品名称、类型、索引简介、访问模式和生命周期。
- 首页精选状态、发布日期、封面和图标。
- 基础兼容性数据。
- 可选的文档集关联与归档信息。

`data.yaml` 只是轻量作品索引，不负责提供获取渠道、源码信息、GitHub 更新、支持链接、页面按钮、功能说明、媒体和特效配置。默认骨架从 `index.mdx` Frontmatter 和正文获取这些页面专属内容；自定义主页在 `index.astro` 中自由实现。两种主页都可以读取索引数据，但索引模型不得反过来限制页面设计。

### 内容底线

无论采用哪种模式，每个介绍页仍应帮助用户理解：

- 这件作品是什么。
- 它能帮助用户做什么。
- 它适用于哪些环境。
- 如何查看文档。
- 如何免费下载或前往第三方平台获取。
- 如何获取必要的支持。

信息的位置和样式可以不同，但不应因为视觉效果而无法找到。

### 核心功能与配图

已确认：介绍页对核心功能进行展示时，每项核心功能需要配图。

- 图片需要与功能直接相关，优先使用真实界面截图、游戏内截图或专门制作的功能视觉。
- 不使用与功能无关的通用装饰图。
- 功能数量、图片比例和展示方式由当前作品的设计决定，不强制大图文交替布局。
- 所有信息性图片需要有意义的替代文本。

### 不作为全站强制内容的信息

以下内容不强制出现在作品介绍页，如果存在，可以由对应文档组织：

- API 与集成
- 迁移说明
- 依赖关系

### 版本与更新

- 作品可以填写可选的 GitHub 仓库地址。
- 静态构建只校验仓库地址；用户加载页面后，由浏览器请求公开 GitHub Releases。
- 未填写仓库地址或没有 Release 时，默认介绍页不显示“版本与更新”标签。
- 版本列表与更新日志合并在同一标签页，同时展示版本名称、Tag、发布日期、发布类型和更新说明。
- 默认骨架按统一规则展示版本与更新；自定义主页可以自由决定它的展示形式和位置。
- 前端不得嵌入 GitHub Token；读取范围限于无需身份验证的公开仓库。
- 页面使用短期浏览器缓存，避免每次切换标签或重复访问都重新消耗 GitHub 的匿名请求额度。
- 加载失败、API 限流或仓库不可访问时只降级这一标签，不影响静态正文和页面其他功能，并提供前往 GitHub Releases 的直接入口。
- 运行时获取的 Release 内容不进入站内静态全文搜索、站点地图或构建期 SEO 正文。
- 用户点击更新记录后前往 GitHub 对应的 Release 页面。

### 特效与工程质量底线

自定义主页可以使用与作品气质相匹配的专属特效，不要求不同作品使用同一套动效系统。但所有作品介绍页仍应满足：

- 关键内容和主要操作不依赖动画完成后才能使用。
- 支持 `prefers-reduced-motion`，减少动画时仍能正常阅读和操作。
- 不自动播放声音。
- 不使用严重干扰阅读和浏览器原生操作的滚动劫持。
- 大图、视频、3D 资源和页面专属代码按需加载，不让首屏下方的内容阻塞初始显示。
- 交互特效同时支持鼠标、键盘和触摸设备。
- 不通过过小文字、过低对比度或隐藏焦点样式换取视觉效果。

## 8. 文档系统

### 文档内容原则

已确认：文档不需要统一栏目。每件作品是一个完全独立的文档集，根据实际内容组织目录。

```text
docs
├── plugins
│   ├── work-a
│   │   ├── index.md
│   │   ├── installation.md
│   │   └── configuration
│   │       ├── index.md
│   │       └── advanced.mdx       # 需要增强组件时使用 MDX
│   └── work-b
│       ├── index.md
│       ├── concepts
│       └── api
├── cores
├── tools
└── general
```

### 文档首页

已确认：文档首页只承担文档搜索和四个分类入口，不直接预览或列出具体作品的文档。

文档首页不设计成第二个官网首页，保持简洁且功能明确。

内容结构：

```text
文档
查找安装、配置与使用说明。

[搜索文档……]

[插件文档]           [核心文档]
查看插件文档集       查看服务端核心文档集

[工具文档]           [通用文档]
查看工具与组件文档   查看不属于特定作品的指南
```

信息密度规则：

- 页面开场只使用标题、一句说明和一个明确的搜索入口。
- 不展示文档数量、浏览数据、更新排行或大段介绍。
- 首页始终只显示插件、核心、工具和通用四个分类入口。
- 不在分类入口下继续展开具体文档集。
- 四个入口的具体视觉形式待视觉稿确认，可以是两列宽松入口或纵向行式入口，但不应呈现密集小卡片。

### 文档分类页

`/docs/plugins`、`/docs/cores`、`/docs/tools` 和 `/docs/general` 点击进入后，以列表形式展示当前分类下的文档集。

文档集的含义：

- 对于插件、核心和工具分类，每一件作品对应一个独立文档集。
- 对于通用分类，每一个独立的通用主题或指南系列对应一个文档集。
- 文档集是侧边栏、上一页/下一页和局部导航的边界。

分类页使用同一套轻量列表语言：

- 页面标题和一句分类说明。
- 不设置营销式首屏。
- 每个列表项对应一个文档集入口。
- 作品文档集的列表项可以展示作品图标、名称、一句文档说明和必要的归档状态。
- 点击列表项后进入该文档集的 `index.md` 或 `index.mdx`。
- 作品数量较少时直接展示全部，不增加无必要的排序和筛选控件。
- 当实际数量增长后再考虑增加筛选，不为了表面丰富提前加入。

### 侧边栏

侧边栏完全根据当前文档集的实际目录生成：

- 文件夹生成分组。
- Markdown/MDX 文件生成页面链接。
- `index.md` 或 `index.mdx` 作为所在目录的入口页；普通入口默认使用 `.md`，需要增强组件时才使用 `.mdx`。
- 支持多级嵌套、折叠和当前页高亮。
- 不同文档集的侧边栏完全隔离，不展示其他作品或其他文档集的页面。
- 进入另一件作品的文档后，应以该作品的文档根目录重新生成一份新侧边栏，不是在同一份侧边栏中切换分组。
- Frontmatter 用于当前页的标题、说明、图标、永久链接、布局以及必要的侧边栏局部控制。
- 不重复维护一份完整的手写侧边栏。
- 当前页所在的目录分支自动展开，其他分支可折叠。
- 侧边栏拥有独立滚动区域，但不干扰正文的浏览器滚动。
- 真实文档如果存在更深层级，侧边栏需要正确展示，不为了视觉统一强制限制文档层级。

每个 `docs/{category}/{documentSet}/` 目录构成一个文档集，不另设文档集 `data.yaml`。根目录必须包含且只能包含一种入口：`index.md` 或 `index.mdx`。根页面的标题、说明和图标同时作为文档集列表信息；仅根页面可以通过 `documentSet` 配置顺序和状态等文档集级字段。作品可以通过 `data.yaml.docs.root` 单向引用一个文档集；文档集不要求关联作品，也不保存反向作品字段。

示例：

```yaml
---
title: 数据库配置
description: 配置外部数据库连接
icon: lucide:database
link: /docs/plugins/example-work/database
layout: default
draft: false
sidebar:
  label: 数据库
  order: 20
  hidden: false
---
```

Frontmatter 中的 `icon` 和 `link` 规则：

- `icon` 是可选项，使用 `lucide:{name}` 引用默认 Lucide 图标，或使用 `local:{path}` 引用 `src/icons/` 中已登记的本地 SVG，例如 `local:docs/database`。
- 配置 `icon` 后，同一图标显示在侧边栏文档标题左侧和正文页标题左侧；未配置时不保留空白占位。
- 不接受原始 SVG、远程 URL 或其他未列入白名单的图标集；所有图标均在构建期从本地依赖或本地 SVG 注册表解析。
- `link` 是可选的页面永久链接。配置后，页面对外 URL、站内链接、搜索索引和站点地图都使用该路径，而文件目录仍用于生成文档层级与侧边栏结构。
- `link` 必须使用以 `/` 开头的站内绝对路径，并且在全站范围内唯一。已经公开的永久链接不应随意修改；确需修改时应同时配置旧地址重定向。

其他页面字段遵循以下规则：

- `title` 必填并由阅读布局生成唯一一级标题，正文从二级标题开始。
- `description` 在普通页面中可选，在文档集根页面中必填。
- `layout` 默认为 `default`，只有宽表格或大型示意图等特殊页面使用 `wide`。
- `draft: true` 的页面只在开发环境可访问，不进入生产构建；根页面为草稿时整个文档集不发布。
- `sidebar.label` 只改变侧边栏文字，`sidebar.order` 控制同级顺序，`sidebar.hidden` 使页面保留直接访问能力但不进入导航、搜索和站点地图。
- `documentSet` 只允许出现在文档集根页面，用于文档集列表顺序和 `active | archived` 状态；归档文档仍然公开并显示状态提示。

### 文档阅读布局

阅读页使用统一的安静阅读外壳，但不干预文档集自身的内容结构。

```text
全站导航                                      [搜索]

自动侧边栏        Markdown/MDX 正文          本页目录
[作品图标] 作品文档    文档 / 分类 / 当前作品      H2
返回作品介绍 ↗       页面标题                  H3
                       可选页面说明              H2
文件夹与页面       正文内容
当前页高亮

                       上一页 / 下一页
```

布局规则：

- 桌面端只保留一条全站顶部导航，不在其下方再叠加一条常驻的文档导航条。
- 左侧为当前文档集自动生成的侧边栏，其顶部同时承担当前文档集的身份识别。
- 侧边栏顶部可以显示作品图标、作品名称和“返回作品介绍”链接，但不展示其他作品的切换器。
- 正文顶部使用轻量面包屑说明当前分类、文档集和页面位置。
- 中间为 Markdown/MDX 正文，使用舒适的阅读宽度，不随视口无限拉伸。
- 右侧根据当前页的二级和三级标题自动生成本页目录。
- 页面标题较少时自动隐藏右侧目录，让正文获得更多空间。
- 需要展示宽表格、API 参考或大型示意图的特殊页面，可以通过 Frontmatter 启用更宽的正文布局。
- 底部只保留上一页和下一页导航，且只在当前文档集内计算，绝不跳转到另一件作品的文档。
- 缺少上一页或下一页时，直接隐藏对应入口。

页面 Frontmatter 示例：

```yaml
---
title: 数据库配置
description: 配置外部数据库连接
icon: lucide:database       # lucide:{name} | local:{path}
link: /docs/plugins/example-work/database
layout: default              # default | wide
draft: false
sidebar:
  label: 数据库
  order: 20
  hidden: false
---
```

### 正文呈现

- 正文字号、行高和段落间距以长时间阅读为优先，不追求过度紧凑。
- 代码块支持语法高亮、复制、长行水平滚动和文件名标识。
- 提示、注意、警告和危险信息使用克制且易于区分的样式，不使用大面积高饱和色。
- 表格优先保持语义清晰，窄屏无法完整展示时使用水平滚动。
- 图片支持说明和点击放大，不把关键文字只放在图片中。
- MDX 可以按实际文档需要提供标签页、可折叠区域和交互示例，不要求所有文档使用相同组件。

已确认移除：

- “这篇文档有帮助吗？”
- “编辑此页面”
- “报告文档问题”

移动端将左侧文档目录和右侧本页目录分别收进抽屉，正文占据主要宽度。

### 移动端文档工具栏

已确认：桌面端不使用第二条导航，但移动端在阅读页使用一条紧凑的文档工具栏，让被隐藏的两个目录仍然容易访问：

```text
[文档目录]    当前作品文档    [本页目录]
```

- 左侧按钮打开当前文档集的自动侧边栏。
- 中间只显示当前作品或文档集名称，过长时截断。
- 右侧按钮打开当前页面的标题目录。
- 工具栏可以粘附在全站导航下方，但高度和视觉重量应保持克制。
- 搜索仍由全站顶部导航中的搜索入口打开，不在文档工具栏中增加第三个按钮。

### 搜索体验

快速搜索与完整结果页的视觉、交互、上下文范围和主题边界由[全站搜索体验](./search-experience.md)统一维护。全站使用同一个搜索入口和搜索界面，不为文档系统再实现一套互不相关的搜索。

入口：

- 全站顶部导航始终提供一个克制的搜索按钮或输入框。
- 文档首页提供一个更明确的大型搜索入口，但打开的仍是同一搜索界面。
- 桌面端支持 `Ctrl/Command + K` 打开搜索，并支持方向键选择、`Enter` 打开和 `Escape` 关闭。
- 移动端搜索使用接近全屏的界面，保留清晰的输入、关闭和返回操作。

搜索上下文：

- 从某个作品的文档阅读页打开搜索时，首先显示当前文档集内的结果。
- 搜索界面仍提供“全部文档”和“全站”范围，但这些结果不会被混入当前文档集的侧边栏。
- 从文档分类页打开搜索时，可以优先展示当前分类下的文档。
- 从文档首页打开搜索时，默认搜索全部文档。
- 从官网其他页面打开搜索时，默认搜索全站。

结果呈现：

- 文档结果显示页面标题、命中摘要和所属文档集。
- 全站搜索结果区分作品、文档和支持内容。
- 隐藏页和草稿页不进入索引；已归档文档可进入索引，但需要显示归档标识。
- 搜索结果需要支持键盘焦点和屏幕阅读器语义。
- 搜索使用 Pagefind 的构建后静态索引和自研界面；完整结果使用独立的 `/search` 路由。

## 9. 支持中心

### 已确认的定位

支持中心是一个单页导向页，不拆分多个 `/support/*` 子页。页面只保留社区与交流、获取与授权、赞助与支持、法律与政策四个主要部分。

需要更完整解释的内容可以链接到“文档 → 通用”中的对应文档集，支持页本身不重复承载长篇说明。

### 页面结构

```text
支持
找到 LunaDeerMC 的社区、作品获取方式、赞助渠道与相关政策。

社区与交流
→ QQ 群
→ GitHub 主页
→ 支持邮箱
→ 查看通用文档

获取与授权
→ 第三方获取平台
→ 获取后的权益与优势

→ 获取、退款与第三方平台说明

```

四个部分使用 `#community`、`#obtain`、`#sponsor` 和 `#legal` 作为页内锚点，方便其他页面直接链接到对应内容。

### 社区与交流

该部分展示：

- QQ 群：群名、群号、用途和加入方式。
- GitHub 主页：用于查看开源作品、源码和公开仓库。
- 支持邮箱：用于不适合在公开社区处理的联系与支持事项。

每个渠道需要简短说明用途，避免用户向错误渠道发送内容。社区规则、提问建议和安全联系说明可以链接到通用文档。

### 获取与授权

该部分展示：

- LunaDeerMC 使用的第三方获取平台及外部链接。
- 获取付费版本后可以得到的主要优势，例如专业功能、持续更新或对应支持权益。
- 退款政策的简短摘要和详细说明链接。

官网本身不处理订单、付款和交付。价格、订单状态、交付和退款规则应明确以第三方平台与详细政策为准，支持页不维护可能过期的详细交易信息。

### 赞助与支持

该部分展示：

- 当前可用的赞助方式和对应外部链接。
- 赞助者可以获得的优先支持。
- 赞助者可以获得的新作品或新功能优先测试机会。

赞助与获取付费作品是两个不同概念，页面需要明确区分。优先支持与优先测试的条件、范围和方式应链接到通用文档，避免用一句模糊文案产生过度承诺。

### 法律与政策

该部分不承载完整条款，只展示必要的政策入口：

- 隐私政策。
- 使用条款。
- 获取、退款与第三方平台说明。
- 第三方软件声明。
- 商标与免责声明。

完整内容组织为“文档 → 通用”下的一个独立“法律与政策”文档集，例如：

```text
/docs/general/legal/
├── index.md
├── privacy.md
├── terms.md
├── obtain-and-refund.md
├── third-party.md
└── trademark-and-disclaimer.md
```

支持页可以链接到该文档集首页或具体政策页；页脚也可以直接链接到具体政策文档，但不再使用 `/legal/*` 路由。

### 视觉与布局继承

支持中心的视觉设计、布局系统、容器宽度、排版、间距、组件风格、动效尺度和信息密度与网站主页保持完全一致，不为该页面另建一套设计定义。四个内容部分只定义信息架构，实际呈现直接使用主页确立的设计语言与基础组件。

## 10. 关于我们

### 页面目标

“关于我们”的主要任务是让用户理解 LunaDeerMC 是谁、为什么开发这些作品、谁在维护它们，以及如何联系或正确使用品牌资源。

页面应当体现开发组织的真实性和人的存在，不使用空泛的企业宣传语、虚构统计数字或无意义时间线。

### 已确认的页面结构

考虑到当前内容规模，使用一个完整的 `/about` 单页，不将每部分拆成内容较薄的子页。

```text
关于 LunaDeerMC
简短的组织介绍

我们在做什么
→ 插件、服务端核心、工具与组件

开发理念
→ 少量真正重要的原则

成员
→ 姓名或网名、角色、个人链接

开源
→ 开源态度、代表作品、GitHub 组织

合作与联系
→ 支持邮箱、合作范围、支持页入口

品牌资源
→ Logo、可用版本、下载与基本使用规则
```

不创建 `/about/team`、`/about/open-source`、`/about/contact` 和 `/about/brand`。对应内容使用 `/about` 的页内锚点；未来某一部分内容足够丰富时，再独立拆页。

### 组织介绍

- 介绍 LunaDeerMC 的组织性质与主要开发方向。
- 解释组织希望解决的问题和长期关注的方向。
- 正文优先使用两到三段真实陈述，不使用“行业领先”、“赋能生态”等无法证明的营销语。
- 不在关于页重复首页的完整作品展示。

### 开发理念

- 使用 3–4 条真正会影响开发决策的原则，而不是罗列大量抽象价值观。
- 每条原则由一个简短标题和一段具体解释组成。
- 原则的具体内容需要由团队确认，不在设计阶段擅自编写。

### 成员

- 只展示成员自愿公开的信息。
- 每位成员可以包含头像、姓名或网名、组织角色、一句介绍及 GitHub 等个人链接。
- 不强制所有成员使用真实姓名或真人照片。

### 开源

- 简短说明 LunaDeerMC 对开源的态度和哪些内容会开源。
- 可以展示少量代表性开源作品，但不重复作品列表的完整目录。
- 提供 GitHub 组织主页入口。
- 作品是否开源从统一作品数据读取，不在关于页另外维护一份状态副本。

### 合作与联系

- 说明支持邮箱适合接收的联系类型，例如作品合作、开源协作、品牌使用或其他非公开事项。
- 技术支持优先引导至支持页中已说明的渠道，避免同一邮箱用途含糊。
- 网站为纯静态站点，第一阶段不建立站内联系表单，直接提供邮箱与外部渠道。

### 品牌资源

- 提供官方 Logo 的主要版本、适用背景和下载入口。
- 简要说明最小留白、变形、改色、与第三方品牌并列等基本使用规则。
- 品牌文件较少时直接在本页提供；资源增多后再拆分 `/about/brand`。
- 商标与免责声明由“文档 → 通用 → 法律与政策”文档集负责，品牌资源区只提供使用指南和下载。

### 视觉与布局继承

关于我们页面的视觉设计、布局系统、容器宽度、排版、间距、组件风格、动效尺度和信息密度与网站主页保持完全一致，不为该页面另建一套设计定义。各内容部分只定义信息架构，实际呈现直接使用主页确立的设计语言与基础组件。

## 11. 全站页脚与辅助页面

### 已确认的全站页脚

页脚的完整内容职责、主题外观与响应式规则由[全站页脚系统](./footer-system.md)统一维护。页脚承担品牌收尾、少量主要入口与必要政策访问，不作为第二套站点地图。


- 第三方声明、商标免责、获取与退款不全部平铺在页脚。
- 外部链接使用明确外链标识。
- 年份在构建时自动生成，不手工维护。
- 品牌页面的页脚跟随当前浅色或深色环境自然收尾；内容页面使用语义表面与极淡分隔线衔接正文。
- 移动端按品牌、主要链接和法律底栏纵向排列，不使用折叠面板。
- 不使用庞大插画、高饱和渐变或密集多列链接制造页脚分量。

### 已确认的 404 页面

404 页面保留全站导航与页脚，中间内容只完成说明和重新导向：

```text
404
没有找到这个页面。

[返回首页]  [查看文档]  [搜索]
```

- 不使用大段解释、幽默文案集或与品牌无关的通用插图。
- 搜索按钮打开与全站一致的搜索界面。
- 如果未来增加自动路由替换，优先直接跳转旧路由，不让可以恢复的链接进入 404。

### 已确认的搜索结果页

建议在快速搜索界面之外，提供 `/search?q={query}` 结果页，用于查看更多结果、保留搜索状态和分享查询链接。

建议结构：

```text
搜索
[查询内容……]

全部    作品    文档    支持

结果标题
所属类型 / 文档集 / 路径
命中内容摘要……

……
```

- 查询内容和结果类型同步到 URL。
- 结果以简洁纵向列表呈现，不使用卡片墙。
- 每个结果显示标题、所属类型、路径与命中摘要。
- 搜索结果为空时，显示简短说明、清除筛选与返回文档入口。
- 快速搜索界面显示有限结果，并提供“查看全部结果”进入该页。
- 具体搜索引擎和中文分词仍留到技术选型阶段确定。

### 其他基础输出

站点在构建时自动生成：

- `sitemap.xml`，包含公开作品、介绍页、文档和通用页。
- `robots.txt`，指向站点地图并排除不应索引的路径。
- 默认站点图标、基础社交分享图和默认元数据。
- 页面跳过导航链接，让键盘用户可以直接进入主内容。

## 12. 内容与作品数据

### 已确认的分层原则

内容分成四层，避免一份庞大数据模型同时承担列表、介绍页和文档的所有内容：

1. **全站配置与固定页面文案**：`src/content/site/data.yaml` 保存站点名称、社区渠道、支持邮箱、GitHub、第三方平台和赞助方式；`src/i18n/{page}.ts` 按页面保存中英文固定文案。
2. **作品登记数据**：每件作品自己的 `src/content/works/{work}/data.yaml` 保存首页、作品列表、搜索、文档关联和 SEO 共同需要的稳定元数据。
3. **页面专属内容**：作品介绍页源码与作品数据放在同一目录；单个 `index.mdx` 使用语言标签保存中英文“介绍”正文，单个 `index.astro` 使用同目录 `copy.ts` 保存双语文案。支持页和关于页使用共享 Astro 页面实现及各自双语文案模块。
4. **文档内容**：所有文档集统一放在顶层 `docs/`，每个文档集内部使用 `zh-CN/` 与 `en/` 独立内容树，与作品介绍页源码分离。

作品介绍页的主视觉、功能图、媒体、内容顺序、布局和交互不放入 `data.yaml`，而是与对应介绍页源码一起维护。数据与页面共置便于管理，但两者仍保持清楚的职责边界。

### 实际源码目录结构

以下结构是第 7、8、12 节共同使用的权威目录模型。更完整的技术分层见《LunaDeerMC 官网技术架构》：

```text
docs/                                 # 文档内容源
├── plugins/{documentSet}/
│   ├── zh-CN/
│   ├── en/
│   └── assets/
├── cores/
├── tools/
└── general/

src/content/site/data.yaml            # 全站与外部渠道配置
src/i18n/                              # 每个文件同时保存对应页面的中英文文案
├── common.ts
├── home.ts
├── support.ts
├── about.ts
├── search.ts
└── errors.ts

src/content/works/
├── example-work/                     # 使用默认骨架的介绍页
│   ├── data.yaml                     # 列表、搜索和全站关联数据
│   ├── index.mdx
│   ├── components/
│   └── styles/
└── another-work/                     # 使用自定义主页
    ├── data.yaml
    ├── index.astro
    ├── copy.ts
    ├── components/
    └── styles/

src/pages/                            # 只负责 Astro 路由
├── index.astro
├── about.astro
├── support.astro
├── search.astro
├── 404.astro

│   ├── index.astro
│   └── [work]/index.astro

```

固定官网页面直接使用 Astro 文件路由；作品和文档作为内容源与 Astro 路由分离，由专用内容层在构建时生成静态路径。

### 全站配置

概念示例：

```yaml
site:
  name: LunaDeerMC
  description: 为 Minecraft 社区构建可靠易用的插件、服务端核心与开发工具。
  url: https://example.com

contact:
  email: support@example.com
  github: https://github.com/LunaDeerMC
  qqGroups: []

obtainPlatforms: []
sponsorshipMethods: []
```

这些可复用渠道不在页脚、支持页和关于页分别手工填写。各页仍可根据自己的设计决定展示方式。

### 作品登记数据

每件作品的索引数据与介绍页共置于 `src/content/works/{work}/data.yaml`。构建系统扫描这些轻量记录生成作品列表、首页精选、搜索数据、默认 SEO 和全站关联；介绍页专属内容不进入该文件。

概念示例：

```yaml
name: Example Work
summary:
  zh-CN: 用于作品列表和搜索的一句说明
  en: A concise description for listings and search
type: plugin                       # plugin | core | tool | component
accessModel: freemium              # free | paid | freemium
lifecycle: active                  # early-access | active | archived
featured: true
publishedAt: 2026-07-18

icon: local:works/example-work

cover:
  src: ./assets/cover.webp
  alt:
    zh-CN: Example Work 封面
    en: Example Work cover

compatibility:
  minecraft:
    - "1.21.x"
  platforms:
    - Paper
    - Folia

docs:
  root: plugins/example-work

archive:
  archivedAt: null
  note: null
  replacement: null
```

字段边界：

- 作品目录名直接作为作品 ID 和介绍页路由参数，不在 `data.yaml` 中重复填写 `id` 或 `slug`。
- `accessModel` 只是列表和搜索需要的访问模式索引，不要求索引文件描述具体获取渠道。
- 归档不是作品类型，而是 `lifecycle` 状态。
- `summary` 只是列表和搜索摘要，不是介绍页的全部文案。
- `name` 是两种语言共用的作品品牌名称；`summary`、可选 `cover.alt` 和归档时必填的 `archive.note` 使用字段优先的 `zh-CN / en` 本地化值。
- `cover` 是必填的首页与作品列表封面，`src` 必填、`alt` 可选；`src` 可以使用作品目录内的本地图片或 HTTPS 远程图片，未填写 `alt` 时按装饰性图片输出空替代文本。介绍页可以使用完全不同的专属视觉。
- `featured` 可选并默认为 `false`；`compatibility` 整体可选，只保留 Minecraft 版本和平台，不记录或展示 Java 版本。
- Minecraft 版本与平台使用开放的非空字符串列表，不设置格式或白名单；完全重复项只警告并保留第一次出现的值。
- 非归档作品可以省略 `archive`，也可以保留三个字段全部为 `null` 的空对象；归档作品必须填写归档日期和说明。
- `publishedAt` 与 `archive.archivedAt` 使用 `YYYY-MM-DD` 纯日期，只校验格式，不限制先后顺序或未来日期；替代作品必须存在且不能指向自身。
- `docs.root` 存在即表示提供公开文档，分类从路径推导，不再维护 `enabled` 或 `category`。
- 一件作品最多通过单个 `docs.root` 关联一个文档集；文档集可以不被任何作品引用，也可以被多件作品引用。
- `docs.root` 必须遵守 `plugin → plugins`、`core → cores`、`tool/component → tools`；作品不得关联到 `general`，后者只用于通用文档集。
- 获取渠道、源码与仓库、GitHub 更新、支持链接、`hero`、`features`、`gallery` 和特效配置都属于介绍页专属内容，不进入作品索引数据。
- 默认主页将 GitHub、授权、相关链接、图库和获取方式放在 `index.mdx` Frontmatter 中；MDX 正文只负责“介绍”标签页。自定义主页在 `index.astro` 中自由编辑。
- 默认作品页 Frontmatter 的精确字段结构与校验规则以[技术架构：默认作品页 Frontmatter](./technical-architecture/default-work-page-frontmatter.md)为准，不在设计说明中维护第二份 Schema。

### 文档集数据

- 所有文档集的名称、说明、图标、顺序和文档状态都由其根 `index.md` 或 `index.mdx` 提供；作品登记数据只负责通过 `docs.root` 建立作品关联，并提供作品本身的生命周期等全站数据。
- 每个作品的 `docs.root` 是文档集边界，侧边栏和上一页/下一页只在该根目录中生成。
- 通用文档不依赖作品登记数据，每个通用文档集在自己的根目录提供名称、说明、图标、顺序和状态。
- 文档页的 Frontmatter 管理当前页标题、说明、图标、永久链接、布局与侧边栏局部控制。
- 完整侧边栏不作为一份独立数据手工维护。

### 构建时校验

构建应当在发布前发现明确的内容错误：

- 作品目录名必须使用全站唯一的小写 kebab-case，并直接作为作品 ID 和路由参数。
- 每个 `src/content/works/{work}/` 必须包含 `data.yaml`，并且只能存在一个有效入口：`index.mdx` 或 `index.astro`。
- `data.yaml` 和 `index.mdx` 中未定义的字段只产生构建警告并被忽略；必填字段缺失或已知字段类型、取值错误时构建失败。
- 结构化文本在标准化记录中去除首尾空白，必填文本不能为空；名称、摘要和标签等短文本保持单行纯文本，不在 Frontmatter 中嵌入 Markdown 或 HTML，也不设置硬性字符数上限。
- 默认 `index.mdx` 必须包含有效的“介绍”正文；仅包含 Frontmatter、模块语句、注释或空白时构建失败。
- 机器标识、推荐状态、标准链接类型和完全相同的渠道发生冲突时构建失败；普通重复文本或非确定性 URL 重复只警告并保留第一项。
- 启用介绍页或文档时，对应入口和 `docs/` 根目录必须存在。
- 作品类型与 `docs.root` 分类不匹配，或者作品指向 `general` 时构建失败。
- 文档 Frontmatter 的 `link` 必须是合法的站内绝对路径且全站唯一。
- 文档 Frontmatter 的 `icon` 必须指向存在的 SVG 资源或受支持图标集中的有效图标。
- 内部链接和图片路径断裂时构建失败。
- 信息性图片缺少替代文本时报错或至少给出强警告。
- 隐藏和草稿内容不进入导航、搜索索引与站点地图。
- 已归档作品必须有归档说明，不再显示无效获取入口。
- 构建阶段不获取 GitHub Releases，只校验仓库 URL；Release 的空数据、限流和网络失败由浏览器运行时处理。

## 13. 视觉与信息密度

### 已确认的个人偏好与设计目标

整体风格应当“简约、大气、高级、有质感”。

核心原则：

> 简约，但不空洞；克制，但有足够的层次与细节。

高级感主要来自：

- 排版比例
- 清晰的字号与字重层级
- 充足但有节奏的留白
- 高质量的真实截图和作品视觉
- 稳定一致的间距系统
- 少量而明确的强调色
- 有明确目的、节奏统一的交互与动态视觉

信息密度原则：

- 一个视觉区域主要表达一个意思。
- 不在首屏堆叠标签、统计数据和功能列表。
- 正文使用适宜的阅读宽度，不在大屏上无限拉宽。
- 次要信息通过渐进展开呈现。
- 避免将每项内容都放入带边框的卡片。
- 标签保持必要数量，不在同一个列表项中展示所有元数据。

首页、作品列表、文档、支持中心和关于我们等全站通用页面应避免：

- 页面中到处都是圆角卡片
- 大量彩色标签
- 过强的玻璃拟态和背景模糊
- 大范围霓虹发光
- 无意义的渐变文字
- 信息密集的仪表盘式布局
- 重复介绍同一内容
- 无目的、持续争夺注意力的动画或滚动特效

整站需要建立统一的沉浸式品牌体验，而不是只允许自定义作品主页具有表现力：

- 首页、作品列表、支持中心和关于我们采用“品牌模式”，可以使用更强的空间层次、动态背景、共享元素转场、滚动叙事和局部交互。
- 文档采用“阅读模式”，延续相同的颜色、字体、材质和品牌氛围，但显著降低持续运动和滚动动画；高级感主要来自排版、留白、层次与细节。
- 默认作品介绍页位于两者之间，可以具有品牌化转场和精致交互，但不能让动态效果干扰信息查找与获取操作。
- 自定义作品主页可以在全站体验基础上使用当前作品专属的视觉语言、动画和可选 3D 效果。
- 所有模式都必须遵守第 7 节的性能、输入方式、可访问性和 `prefers-reduced-motion` 底线。

全站页面的双主题和自定义配色边界以[全站主题策略](./theme-strategy.md)为准：包括首页、支持中心和关于我们在内的通用页面支持浅色与深色；自定义 `index.astro` 作品页自行决定配色与主题行为。

## 14. 实现阶段仍需校准

以下内容不应在实现时擅自视为定稿：

- 首页正式生产插画的细节精修、压缩格式与性能预算。
- 是否真的需要 Canvas、WebGL、3D 或 Shader，而不是为了“高级感”先行加入技术效果。
- 文档版本化方案。
- 第三方获取平台的具体名称和链接。
