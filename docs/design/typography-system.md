# 全站排版系统

> 本文档定义 LunaDeerMC 官网的字体选择、字体职责、双语排版边界和基础比例原则。

- 最后更新：2026-07-23
- 状态：字体家族、基础字号层级、阅读宽度与双语排版约束已确认；实现令牌待视觉稿校准

## 总体结论

网站全局支持中文和英文。排版系统使用三个字体角色：

```text
Mona Sans
├── 英文品牌标题
├── 英文界面与正文
├── 数字、版本与拉丁标点
└── 中文内容中的拉丁字符

中文系统字体栈
├── 中文标题
├── 中文界面与正文
└── 中文标点与完整汉字覆盖

JetBrains Mono
├── 代码
├── 命令与配置
└── 必要的快捷键和技术数据
```

全站不使用 Minecraft 像素字体、装饰性衬线字体或刻意制造“科技感”的字形作为主要排版。Minecraft 关联由场景、作品和图像内容承担。

## 字体加载策略

- 自托管 Mona Sans 可变字体，覆盖英文品牌、英文正文、界面文字、数字和常用拉丁标点。
- 自托管 JetBrains Mono，专门用于代码、命令、配置和技术数据。
- 中文使用可靠的系统中文字体栈，不要求首屏下载完整中文网络字体。
- 代码使用独立等宽字体；中文出现在代码或终端内容中时，回退到具有完整字形覆盖的系统等宽或中文字体。
- 第一阶段不将完整中文字体文件作为首屏必需资源。
- 如果后续采用中文字体子集或 `unicode-range`，必须验证动态文档、作品名称、生僻字、中文标点和构建更新不会产生缺字。

这套策略优先保证静态官网和长篇文档的首屏速度、字符覆盖与渲染稳定性，同时让英文品牌表现保持一致。

## 字体家族与回退顺序

全站常规内容使用：

```css
font-family:
  "Mona Sans",
  "PingFang SC",
  "Microsoft YaHei UI",
  "Microsoft YaHei",
  "Noto Sans CJK SC",
  "Source Han Sans SC",
  system-ui,
  sans-serif;
```

实际中文字体随平台确定：

- macOS 与 iOS 优先使用苹方 `PingFang SC`。
- Windows 优先使用 `Microsoft YaHei UI`，不存在时回退到 `Microsoft YaHei`。
- Android 和常见 Linux 环境优先使用 `Noto Sans CJK SC`。
- 安装了思源黑体的 Linux 环境可以回退到 `Source Han Sans SC`。

Mona Sans 位于字体栈首位，因此英文、数字、版本号和常用拉丁字符保持一致；其不包含的汉字与中文标点自动落入系统中文字体。不得为了让所有平台看起来完全相同而强制下载完整中文字体。

代码内容使用：

```css
font-family:
  "JetBrains Mono",
  "SFMono-Regular",
  Consolas,
  "Liberation Mono",
  monospace;
```

中文代码注释所需的汉字继续由平台可用字体回退补齐。代码字体不能用于普通技术说明、版本标签或导航，以免网站出现过重的“开发工具界面”感。

## 选择理由

- Mona Sans 在克制的现代无衬线基础上保留了一定辨识度，适合首页英文 Hero，也能覆盖界面和英文长文。
- 其可变字重、字宽与光学尺寸能力允许标题和正文共享一个家族，同时避免机械放大产生的粗糙感。
- JetBrains Mono 针对代码辨识度与小字号阅读优化，更适合文档中的代码块、行内代码和终端示例。
- 两款字体均采用 SIL Open Font License 1.1，可以随静态网站自托管。
- 不采用 Minecraft 像素字体承担品牌识别；Minecraft 关联继续由环境场景、作品内容和视觉细节表达。

## 双语选择约束

具体拉丁字体必须同时适合：

- 大尺寸英文 Hero 与品牌口号。
- 导航、按钮、标签和搜索等小尺寸界面文字。
- 英文作品介绍和长篇文档正文。
- 代码之外的版本号、日期和技术参数。

因此不能只选择一款适合海报标题、却不适合长时间阅读的展示字体。

中英文混排需要重点验证：

- 拉丁字体与系统中文字体的视觉字面高度和粗细关系。
- 英文大写、数字与中文方块字并列时的基线。
- 中英文括号、引号、冒号、破折号和空格规则。
- 导航、按钮和标题在两种语言下的宽度变化。
- 英文长单词、文档路径和代码标识符的换行。
- 中文标题与英文标题在相同层级中的视觉重量，而不是机械使用完全相同字号。

页面根元素必须使用正确的 `lang` 属性；中文与英文可以共享字号等级，但允许使用不同的行高、字距、断行和微调令牌。

## 字重

排版层级不依赖粗黑字堆叠：

```text
英文 Hero            300–400
页面大标题            450–550
区块标题              500–600
导航与按钮            450–550
正文                  400
强调文字              500–600
```

- 不大面积使用 `700–900`。
- 当前页、悬停和选中状态不通过改变字重造成布局位移。
- 若最终可变字体不提供 `450` 或 `550` 等中间权重，使用最接近且视觉稳定的实际权重。
- 中文系统字体在不同平台可用字重不同，必须为缺少某些字重的环境准备安全回退。

## 字号与行高关系

全站采用连续变化的流动字号，不在响应式断点处突然跳变。实现时优先使用 `clamp()`，以下数值表示视觉设计范围而不是要求每个层级都创建独立组件：

| 层级 | 建议范围 |
| --- | --- |
| 辅助信息 | `13–14px` |
| 导航与按钮 | `15–16px` |
| 普通正文 | 移动端 `16px`，桌面端约 `17px` |
| 重要引导文字 | `18–20px` |
| 卡片标题 | `20–24px` |
| 区块标题 | `28–40px` |
| 普通页面标题 | `36–52px` |
| 首页英文 Hero | 移动端约 `42px`，桌面端最高 `64–72px` |

### 品牌页面

- 英文 Hero 是最大文字，但不能压满整个视口或遮蔽主要场景；视觉冲击主要由四层插画、景深、构图和留白承担。
- 页面标题约为正文的 `2.5–3` 倍，可根据中英文分别微调。
- 区块标题约为正文的 `1.5–2` 倍。
- 英文大标题行高可以接近 `1`，中文大标题需要略更宽松的上下空间。
- 首页主文案建议以轻字重自然排为两行：

  ```text
  To the moon, to the dream,
  to the future!
  ```

  实际断行仍需在不同视口宽度下验证，不允许为了固定断行导致窄屏溢出。

### 内容与文档页面

- 文档一级标题明显小于首页 Hero。
- 文档正文在移动端使用 `16px`，桌面端约为 `17px`。
- 中文长文行高约为 `1.8`，正文列最大宽度约为 `38–42em`。
- 英文长文行高约为 `1.65`，正文列最大宽度约为 `66–72ch`。
- 代码字号可以略小于正文，但必须保持清晰。
- 正文列按当前语言选择理想行长，不能只用一个固定像素宽度解决所有语言。
- 移动端优先减少页面横向留白，不通过继续缩小正文来容纳内容。

## 语言相关排版行为

- 中文正文不使用英文自动断词；英文长文可以在确认浏览器和内容行为后启用合适的 `hyphens`。
- 不对中文标题人为增加大字距制造“高级感”。
- 英文品牌标题可以使用轻微负字距，但正文保持自然间距。
- 中文长段落、英文文档正文和混排内容都不使用居中对齐。
- 导航与按钮不能以中文文本宽度为唯一设计依据，英文标签必须在相同组件中完整容纳。
- `作品 / Works`、`文档 / Docs` 等翻译后的长度变化需要参与导航折叠断点测量。
- 搜索输入提示、空状态、政策名称和辅助说明均需要分别为两种语言编写，不能依赖运行时逐词拼接。

## 自定义作品页

自定义 `index.astro` 作品页可以使用作品自己的局部字体，但：

- 全站导航与必要返回入口仍需保持可识别的品牌排版。
- 页面必须同时说明中文和英文版本的字体行为。
- 局部字体不能污染其他页面的全局字体变量。
- 缺少作品专属字体或加载失败时，需要回退到全站排版系统。
