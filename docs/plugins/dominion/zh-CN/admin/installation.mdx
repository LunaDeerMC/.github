## 兼容性基准

本文档以 Dominion `4.9.1-release` 在 Minecraft `26.2` 上的实际验证结果为基准。项目当前的发行版元数据还列出 `1.20.1–1.20.6`、`1.21.x` 和 `26.1.2–26.2`，平台包括 Bukkit、Spigot、Paper 与 Folia。不同服务端核心和小版本的事件实现可能不同，生产环境应以目标版本启动日志和实际测试为准。

## 新服务器安装

1. 先单独启动一次目标服务端核心，让 `eula.txt`、世界和 `plugins/` 目录生成；确认 Java 版本满足该核心的要求。
2. 将 Dominion 发行版 JAR 放入服务端 `plugins/` 目录。不要同时放入同一插件的多个版本，也不要把源码工程或开发依赖放进 `plugins/`。
3. 启动服务器，等待插件第一次生成 `plugins/Dominion/`。首次启动时不要立刻覆盖生成文件，先保存一份原始配置作为对照。
4. 检查插件是否完成启用。当前 26.2 实测日志包含以下类型的信息：

```text
[Dominion] Loading server plugin Dominion v4.9.1-release
[Dominion] NMS implementations loaded for version: v26_2
[Dominion] Loaded Dominion Dialog NMS backend for Minecraft 26.2.
[Dominion] Database connected successfully.
[Dominion] Plugin Enabled!
```

5. 停服后备份整个 `plugins/Dominion/`，再根据[配置文件总览](./configuration)修改策略。
6. 启动后用普通玩家账号创建一块小型测试领地，分别验证访客、成员、权限组和环境 flag；不要只用 OP 账号判断权限是否正确。

## 生成的目录

不同发行版可能会附带或延后生成部分文件，但生产环境通常会看到以下结构：

```text
plugins/Dominion/
├── config.yml
├── flags.yml
├── limitations/
│   └── default.yml
├── world-wide/
├── languages/
├── dominion.db                 # 使用 SQLite 时
└── logs/                       # 若发行版启用独立日志
```

数据库文件名和具体附属文件应以当前发行版生成结果为准。数据库不要用文本编辑器直接改表；需要备份、迁移或修复时，优先使用插件提供的导出、导入和迁移命令。

## 升级顺序

升级前应先记录当前插件版本、Minecraft 核心版本、Java 版本、数据库类型和配置改动。推荐顺序如下：

1. 停服并完整备份 `plugins/Dominion/` 与服务端日志；外部数据库另外做数据库级备份。
2. 阅读目标版本的变更说明，确认数据库、配置 `version`、flag schema 和 NMS 支持情况。
3. 替换插件 JAR，保留数据目录；不要在没有备份的情况下删除旧数据库。
4. 启动一次，观察是否出现配置迁移、数据库连接或 NMS 加载错误。
5. 先用只读方式检查原有领地，再用测试账号执行创建、边界调整、成员加入和 UI 打开。
6. 确认稳定后再开放玩家；若发生异常，停服保留日志，不要反复启动覆盖现场。

## 常见安装误区

- 把 `api-version`、服务端版本和 Dominion 支持范围混为一谈；能加载不代表所有 UI 或事件都已验证。
- 直接复制旧版 `config.yml` 覆盖新文件，可能漏掉新键或带入旧 schema。更稳妥的做法是比较差异后迁移自己的改动。
- 修改配置后只重载了 `cache`，却期待数据库或语言文件改变；配置策略应使用 `/dominion reload config`，数据库操作则应按命令说明执行。
- 在 OP 账号下测试并得出“所有玩家都能使用”的结论。管理员绕过开启时，OP 的结果不能代表普通玩家。
